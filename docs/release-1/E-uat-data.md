# E. UAT data and configuration pack

## Purpose

UAT is only as convincing as its data. This task builds a fictional multinational, its configuration, a realistic set of files at the agreed size (50 entities, 40 currencies, 20,000 GL balance rows), a demo execution simulator that plays the part of the trading platform, and an independent check that the platform's numbers are right.

**Data design (E1, E2) starts now. Files (E3) wait for D step D1. The simulator (E5) can start now because the executed-trade layout already exists. The rehearsal (E7) needs A (built), D and J merged.**

## Read first

- The Release 1 outline, scenarios section (kept by Fikre in Claude Docs; ask for a copy if you do not have it).
- `app/src/end-to-end.db.test.ts`: the helpers `tenantWithProgram`, `sendBalances`, `sendRates` show every command a configuration needs, in order. `app/src/volume.db.test.ts` (stream A) builds 45 legal entities, 40 currencies and a 20,000-row batch in code: reuse its shape for sizes.
- `services/hedge-recommendation/src/policy.ts` (`PolicyInput`) and decisions 0016, 0020, 0021, 0022.

- `docs/decisions/0014` (calendars), `0015` (exposure currency per pair), `0023` (runtime: the scheduler is a real platform user).
- `docs/file-layouts.md` once D1 is merged.

## Rules for the data

- Everything is fictional: company, entities, bank names, people. No real customer data, no real bank or brand names. Holiday dates are illustrative and say so in the data guide.
- Everything is generated by a script from one seed, so the same seed gives byte-identical files. Large generated files are not committed; the generator, a manifest with file names, row counts and SHA-256 checksums, and the small files (master data, configuration) are.
- Amounts are text with their real number of decimal places (JPY and KRW none, others two). No floating point in the generator: use `decimal.js`.

## Steps

### E1. Data design (a short document, `docs/uat/data-design.md`)

Defaults, to be refined and agreed with Fikre in the PR:

- **Company**: one group, 4 regions (AMER, EMEA, APAC, LATAM), 45 legal entities, for 50 entity records in total. Three are treasury entities and two are hedge execution entities. Every legal entity has a functional currency from the 40.
- **Currencies**: 40, including USD (reporting and display currency, pivot) and at least 6 non-deliverable ones; at least 2 currencies have a Friday and Saturday weekend.
- **Chart of accounts**: one chart with about 25 hierarchy nodes and 40 accounts; 30 are monetary and FX-relevant (cash, trade receivables and payables, intercompany loans and balances, deposits, accruals); the rest are not (inventory, equipment, equity) and are excluded by the mapping rules.
- **GL balances**: 20,000 rows per daily file. Each legal entity holds its functional currency and 6 to 12 others; each row is unique on entity, account, currency and dimensions; some rows carry a `cost_center` dimension. About 5% of rows are non-FX accounts. The file balances are realistic, not random: payables roughly offset receivables in some pairs (natural netting is visible), some entities are net long and some net short, and intercompany balances exist in both directions.
- **History**: 20 consecutive business days of GL files (day-over-day moves of a few percent), 12 months of daily rates, 12 months of executed hedge trades.
- **Two fixtures for bad data, kept apart by where the failure must happen.** Each has exact expected results, written to `packs/uat/expected/` and the data guide.
  1. **Malformed file** (`gl-malformed.csv`, 20,000 rows): exactly 40 planted file-level problems that D's parser must refuse: balance together with debit or credit, neither balance nor debit/credit, a bad date, a bad currency code, a non-numeric amount, a missing required cell. Expected: `INVALID_FILE`, exit code 1, all 40 problems listed by row number and column, and **no rows stored**. Nothing in this file is meant to reach a service.
  2. **Parser-valid dirty file** (`gl-dirty.csv`, 20,000 rows): every row passes the parser and is accepted for storage, and a known number of rows have service-level problems: an unknown entity, an unknown account, an account the mapping rules exclude. Expected: the load is `APPLIED`, and the service's own data-quality result (Data Source's batch result and the issues Exposure Analysis raises) counts exactly these rows by kind. Read what those services return today and write the expected counts from it; if the contract cannot show the count for a kind, write DECISION REQUIRED rather than guess.
  A **missing rate** is a rates-stage condition, not a file problem: it belongs to the rates data (see E3) and is checked where rates are checked (the exposure or recommendation step, e.g. `NO_RATE`), never in either fixture above.
- **Programs and tenants** (Overview table **#9**, confirmed by Fikre 2026-11-20): one tenant per program, because a tenant may run only one balance sheet program today. Two UAT tenants load the same master data, rates and GL files, so the data is generated once. Tenant 1 runs `BS-ENT` (daily, ENTITY netting); tenant 2 runs `BS-REG` (weekly, REGION netting). Each tenant has its own mapping rules, hedge policy and users. The size target applies to each tenant. Do not change the one-program rule in this stream.
- **Hedge policy** (decision 0020 allows one strategy per program, and threshold overrides by netting level only): `BS-ENT` uses hedge-ratio-adjustment at 75% with one pair at 90% (the per-pair ratio override) and rolls with Adjust + Swap; `BS-REG` uses amount-threshold with one program threshold in USD, no override, and has no roll. Both have a minimum hedge amount, rounding by currency, tenor 3M, a trading entity and a maximum hedge. Keep the sample inside the current contract (`PolicyInput` in `policy.ts`); do not use a combination the policy check refuses.
- **Users** (in each tenant): one tenant admin, one analyst, one reviewer, one approver, one viewer, and one platform user. Segregation of duties stays **on**, as a real customer would run it, so approvals need two different people.

Done when: the design is merged and Fikre agrees.

### E2. Configuration script

`npm run uat:configure -- --config packs/uat/config.json`, code in `scripts/uat/configure.ts`. It calls the real commands through `composeApp`, in the order the helpers in the end-to-end test show: create the two tenants (one per program); create the platform user and enable each tenant's program; add the users and grant roles; define the programs (type, netting level, bucket scheme, schedule, effective date); leave segregation of duties on; add the mapping rules; set each program's hedge policy; set the rate settings (preferred source, stale-after, pivot currency, outlier share). `config.json` holds everything that is a choice; the script holds none.

- It refuses to run if either tenant name already exists (how it checks is E's open question about tenant names; do not add an Identity rule here). It never deletes anything. A separate `npm run uat:reset` drops the service schemas, and refuses unless the database name ends in `_uat` or `_test` (same list the end-to-end test drops).
- Users are created with `issuer` and `externalSubject` taken from the config (`OIDC_ISSUER` and the user name). Sign-in work (C) will decide the claim that must match; leave `externalSubject` a plain config value so C can change it in one place.
- Master data (entities, hierarchy, accounts, currencies, calendars, exposure currencies) is **not** loaded here: it is loaded by D's loader from E3's files, so the same path as a customer's.

Done when: a test runs it twice on a `_test` database, the second run refuses, and the first leaves two tenants that can each start a cycle.

### E3. Generator (after D1 is merged)

`npm run uat:generate -- --seed 20261120 --out packs/uat/generated` in `scripts/uat/generate.ts`. It writes, in the layouts of `docs/file-layouts.md`: the six master-data files; 20 daily GL files plus the two bad-data fixtures (malformed and parser-valid dirty); 12 months of daily rate files (spot for 39 pairs against USD; forwards for 1M, 3M, 6M, 12M); and the history of executed trades in the executed-trade layout. Rates move as a seeded random walk with realistic daily volatility per currency, and forward points follow from interest differentials in the config.

Plant, and list in the data guide, these things in the rates and balances (the two bad-data GL fixtures in E1 are generated as well, with their expected results): a missing rate on one day for one pair; a stale rate; an outlier rate that is flagged; a holiday on a value date; one currency whose balances flip from long to short between two days; one entity with all its balances excluded. Run the generator twice and compare checksums: a test fails on any difference.

Done when: the regular files load with D's loader without a single problem; the malformed file is refused with exactly its 40 problems and stores nothing; the dirty file loads and its service-level issues match the expected counts, and the checksums are in the manifest.

### E4. Independent expected results

`scripts/uat/expected.ts`: reads the generated GL files, rates and the config and computes, with `decimal.js` and **no platform code**, the net exposure by entity and pair (and by region and pair for the weekly program) for each day. It writes `packs/uat/expected/<date>.csv`. This is how UAT knows the platform is right. Where the platform's rules are subtle (netting, bucket, exposure currency of a pair, rounding), implement them from the decision records, and write down in the data guide each rule you implemented and its source. If a rule is unclear, write DECISION REQUIRED; do not guess.

### E5. Demo execution simulator (can start now)

`npm run uat:simulate -- --pretrades <file> --trade-date <date> --seed <n> [--partial <share>] [--reject <share>] --out <file>`. It reads a pre-trade file (header `OUT_HEADER` from `file.ts`, as written by `toPreTradeFile`) and writes an executed-trade file in the executed layout:

- Each executed row keeps `pre_trade_reference`, `hedging_program_id`, `trading_entity`, `instrument`, `leg`, `buy_sell`, `deal_currency`, `deal_amount`, `settlement_currency`, `value_date` and `fixing_date` from the pre-trade; it adds `trade_id` (`SIM-<date>-<n>`), `execution_platform_id` (`SIMFX`), `counterparty` (round-robin from five fictional banks), `trade_date`, and `portfolio` from the config.
- `--partial` executes only that share of the rows chosen by the seed; `--reject` leaves that share out entirely. With neither, every row is executed. Both leave the file valid for the importer.
- Same input and seed give the same output. Both legs of a swap are treated together: never execute one leg without the other unless the option says so.

Done when: a database test takes a recommendation through approval, release, the simulator and the FX Trade import and ends with every executed trade matched to its pre-trade.

### E6. Data guide

`docs/uat/data-guide.md`: the company at a glance, how to load the pack (the exact commands in order), each planted condition, the stage that must catch it (parser, service data-quality, or rates) and its exact expected result, and a table mapping each UAT scenario in the outline to the files and dates that trigger it and the expected result (cite the expected CSV). Fikre's edit to scenario 9, "Next cycle begins with all outstanding hedges including the ones executed in the prior cycle", is the rule for that scenario.

### E7. Rehearsal (needs A, D and J merged)

`npm run uat:rehearse`: on an empty `_uat` database, runs the whole pack: migrate, configure, load master data, rates and 20 days of GL, run cycles, compare every exposure with `expected/`, approve both gates with two users, take the recommendation, release it, run the simulator, import the executed trades, run the next cycle and confirm the executed hedges are included. It prints the time per stage and fails with a diff of any number that differs. This is the acceptance test of A, D, E and J together.

## Not in this task

Anything that needs the screens, sign-in or API; other data types; real customer data; changes to platform rules (if the expected results disagree with the platform, report it: a bug is a finding, not something E fixes in passing).

## Done when

1. E1 to E7 are merged, with a decision record for any rule choice made in E4.
2. The rehearsal passes on a fresh `_uat` database, and its timings at 20,000 rows are in the PR.
3. The same seed gives identical checksums on two machines.
4. `docs/STATUS.md` records what the pack contains.
