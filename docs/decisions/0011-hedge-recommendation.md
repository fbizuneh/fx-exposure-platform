# 0011 Hedge Recommendation: hedge-ratio-adjustment

Date: 2026-11-20. Service: hedge-recommendation (core tier). Sources: The Core Flow (recommend, decide, follow up), decision 0009 (pre-trades), decision 0010 (net exposure), the product owner's answers of 2026-11-19. Written from those answers and my earlier plan; please check it against what you intended.

## Decided
1. **Strategy `hedge-ratio-adjustment`.** An incremental hedge toward a target ratio. Later strategies (a roll-based process with swap plus adjustment, and an amount threshold in place of a target ratio) are added beside it; each recommendation records its strategy.
2. **Calculation, per net exposure group of the run** (decision 0010): target hedge = minus ratio times gross exposure, in the exposure currency. Needed = target minus the outstanding hedges. The needed amount is rounded down (toward zero) to the rounding step, then tested against the minimum. A negative amount sells the exposure currency; a positive one buys it back (an over-hedge).
3. **Target ratio.** Default 100%, with an override per currency pair.
4. **Minimum hedge amount** is set once per program in the display currency. The application converts it to the exposure currency with the spot rate for the as-of date and tests the rounded recommended amount against it in the exposure currency. Below it, no action.
5. **Rounding.** A default (1,000 units of the exposure currency) with an override per exposure currency. 234,430 rounds down to 234,000 at 1,000.
6. **Groups with no action are kept** with the reason (within target, rounds to zero, below minimum, no rate) so the cycle record shows they were looked at.
7. **Instrument and legs.** A forward in the exposure currency (deal currency = exposure currency, settlement currency = the other currency of the pair); an NDF with a fixing date two weekdays before value when the exposure currency is flagged NDF in Master Data. The settlement amount is empty: a pre-trade has no price.
8. **Value date** = as-of date plus the policy tenor (default 1M), rolled forward to a weekday. Weekdays only for now: per-currency business-day calendars in Master Data are a follow-up.
9. **Policy** (per program): default ratio, ratio overrides by pair, minimum in display currency, rounding default and overrides by currency, tenor, and the default trading entity (item 15). Changed with `hedge-policy:manage` on the program. With no policy saved the defaults above apply.
10. **Lifecycle.** A recommendation is open, then accepted, overridden (a user changes the amount, never the direction), dismissed, or lapsed. Undecided ones lapse when the cycle is approved. Decisions save who and when. Accept and override need `hedge-recommendation:accept` / `:override`, dismiss needs `:dismiss`, all on the program. No decision is possible before Approve Exposure (item 17).
11. **Only the winning decision can make a releasable pre-trade.** A decision is won in one atomic step in this service's own database: the first of accept, override or dismiss to change an open recommendation wins and the others are refused. An accept or override records its amount and moves to *deciding*; the pre-trade is then made in FX Trade from that recorded amount (FX Trade keys it by the recommendation ID, so repeating is safe) and a second step confirms the decision. No transaction spans the two services. If FX Trade refuses outright, the recommendation goes back to open (or lapses, if the cycle was approved meanwhile) and no draft exists. If the outcome of the call is unknown, the service looks in FX Trade before concluding anything; if the draft exists it is the one recorded, and if not the decision stays recorded: dismissal is refused, and retrying the same decision finishes it with the recorded amount. At approval, a deciding recommendation with a pre-trade is confirmed and one without lapses, so approval can never release a draft that no recorded decision stands behind.
12. **Recalculation.** Before Approve Exposure (item 17) a recalculation replaces the cycle's recommendations: the earlier ones become superseded and none of them can be decided. After it there is no recalculation, so no replacement recommendation can appear, and that includes while a decision is in progress. The one thing still done after the approval is making recommendations for the approved run itself, if its "run finished" event arrives late.
13. **Follow-up** follows the pre-trade: open (draft, ready, sent), partly executed, executed, cancelled. FX Trade's "executed trade received" event refreshes it.
14. **Events** (identifiers only): recommendations issued (cycle, run); pre-trade created (recommendation, pre-trade).

15. **Trading entity follows the netting dimensions** (product owner, PR #3). When the group has an entity (entity, or region by entity) the pre-trade is booked by that group's entity, never the policy default. When the group has none (group natural, region, portfolio) the program's default trading entity is used. If that is not configured the group gets no actionable recommendation, with the reason `NO_TRADING_ENTITY` and a message telling the user to configure a default trading entity. An executed hedge booked by an entity is counted in that entity's group in the next cycle (decision 0010). FX Trade still checks that the entity is a hedge execution entity.
16. **Pair overrides are unordered.** A ratio override for `USD-EUR` applies to the `EUR-USD` group; the two are the same pair. Saving both is rejected as a duplicate, as is a pair of one currency.

17. **Two approval gates** (product owner, PR #3). **Approve Exposure** is a separate gate in Exposure Management (permission `exposure:approve`), taken once the cycle's run has completed. It locks the exact run that completed, and with it the executed-trade versions that run used (its saved hedge rows name them). Before it, users can recalculate and preview recommendations, but accepting, overriding or dismissing is refused and no pre-trade is made. After it: Exposure Management refuses a rerun; Exposure Analysis locks that run and ignores any new "cycle initiated" for the cycle; and a decision is accepted only for a recommendation made from the approved run (one from any other run is refused). A trade that arrives after the approval, even one with an earlier trade date, does not change the approved positions or recommendations; the next eligible cycle picks it up. Approving and recalculating at the same moment cannot both succeed: they serialize on the cycle, and the loser is refused. **Approve Cycle** stays a separate, later gate: it needs the exposure to be approved first, and it is what releases draft pre-trades to ready. Accepting or overriding after Approve Exposure makes a draft; only Approve Cycle releases it. The one-decision guard (item 11) is unchanged.

## Defaults I chose, to confirm or change
- The calculation uses gross exposure and outstanding hedges from decision 0010, so it never double counts a hedge.
- No maximum hedge amount yet.
- A recommendation that is *deciding* (item 11) is not shown as accepted until FX Trade confirms the pre-trade exists.
- Approve Cycle now requires Approve Exposure first. `exposure:approve` is held by the approver and admin roles. Skipping a cycle is still allowed after Approve Exposure; its undecided recommendations lapse.
- Segregation of duties (approver differs from the decider) is not enforced in this change; it needs an approval guard in Exposure Management and comes next.
- Business-day calendars are weekdays only until Master Data holds them.
