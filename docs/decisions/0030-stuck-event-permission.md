# 0030 — Stuck events: who may see and retry them

Date: 2026-11-21. Services: identity (permission), app/ (`operations.ts`), and every service's `outbox.ts`/`index.ts`/contract (the atomic retry-and-announce, confirmed after review — see point 4). Source: `docs/release-1/J-backend-gaps.md` (J3), confirmed as decision row #8 (Overview table) by Fikre on 2026-11-20.

## Decided

1. **New permission `operations:manage-events`**, added to Identity's `PERMISSIONS`. Held by `TREASURY_ADMIN` (which is `new Set(PERMISSIONS)` — every permission, automatically) and by the platform role (`decide()` already allows `SYSTEM_ADMIN` everywhere, before any tenant-specific facts are even loaded). No other role's permission set lists it, so no other code change was needed in `roles.ts`.
2. **Guarded functions live in `app/src/operations.ts`, not in `dispatch.ts`.** `dispatch.ts`'s `deliveryProblems`/`retryStuckEvent` stay exactly as they are (decision 0019): unguarded primitives the drain loop and tests already use. `operations.ts` wraps them with `checkAccess` and returns the done-when shapes J3 asks for:
   - `listDeliveryProblems(app, actor, filter?)`: with `filter.tenantId` given, one `checkAccess` call against that tenant (works for both a tenant admin and the platform role — the platform role is allowed regardless of which real tenant is named, since `decide()` short-circuits before touching tenant facts). With no filter, the function discovers which tenants the actor may see by checking every tenant that is either active or currently has a delivery problem, and returns the union's events; if that set is empty, it refuses rather than silently returning nothing, so a role with no access anywhere is told so.
   - `deliveryProblemSummary(app, actor)` takes no tenant at all, so it always uses the same discovery path: counts are only ever taken over tenants the actor may see.
   - `retryDeliveryProblem(app, actor, { service, tenantId, eventId })`: one `checkAccess` against the named tenant, then looks the event up **within that tenant** from the raw `deliveryProblems` list before calling `retryStuckEvent` — `retryStuckEvent` itself has no tenant check, so this lookup is what stops a tenant admin reaching another tenant's event with a guessed ID. "Not stuck" is reported from the same lookup (the event is retrying automatically; there is no third state left once `deliveryProblems` already filters to `attempts > 0`).
   - Errors: a bad permission throws `AccessDenied` (same `not allowed (operations:manage-events): <reason>` shape Audit's own `access.ts` uses for `audit:read`); a missing or non-stuck event throws `RangeError` with the state named.
3. **Every use of the platform role is already recorded, for free.** `checkAccess` itself announces `platform-role.used` whenever `decision.via === "platform-role"` (decision 0001), so calling it from `operations.ts` for every list/summary/retry means the platform role's use of this permission lands in Audit with no extra code. That announcement goes through Identity's own outbox and needs a `drain` to reach the trail, like any other change record.
4. **Final (confirmed with the product owner, 2026-11-21, superseding every earlier round below): the retry and its audit announcement are written together, in the owning service's own outbox transaction — Option A from the DECISION REQUIRED below.** Each service's `outbox.ts` `retryStuck(db, eventId, { tenantId, actor })` now resets the event and, in the *same transaction*, announces `<service>.change-recorded` (`event.retried`) into that service's own outbox via its existing `announce`. The UPDATE that resets the event is itself scoped by `tenant_id`, not only `event_id` — the mutation enforces the tenant match directly, not only `operations.ts`'s lookup above it, caught in review ([Buddy]'s re-review of `0267446`). `dispatch.ts`'s `retryStuckEvent` and `operations.ts`'s `retryDeliveryProblem` just pass the actor and tenant through; neither writes to Audit directly any more, and no `recordOperation` addition to Audit's contract was needed (settled separately below). The shape: `action: "event.retried"`, `targetType: "stuck-event"`, `targetId` the plain event ID (not composite), `fields: []`, `programId: null`. The trail's `source` is derived automatically from the event's `type` prefix (`services/audit/src/record.ts`), so it reads the *owning service's* name (e.g. `"fx-rate"`), not `"operations"` — it is that service's own outbox that changed, and that is the most accurate source. This replaces every earlier shape discussed below (the original `targetType` = service name, and the round-2 composite `targetId`) and closes the DECISION REQUIRED: the retry can no longer commit without its announcement, or the other way around, because the database will not let one half of one transaction survive the other.
   - **Ordering exception, narrow and one-sided.** Decision 0019's per-tenant-per-service hold ("nothing is delivered behind an event that is waiting or stuck") would otherwise block a retry's own announcement whenever the event it is about fails again before the announcement is delivered — a real case, since the announcement's sequence number is always higher than the event it reports on. Every service's `pendingEvents` exempts exactly the retry announcement from *being blocked*: a row whose own `type` ends `.change-recorded` **and** whose payload's `action` is `event.retried` is never held behind an earlier unresolved event. It gets no exemption from *blocking others* — if the announcement itself fails to deliver (Audit briefly down, say) and reaches stuck, a later row of the same tenant and service queues behind it exactly as it would behind any other stuck row, preserving decision 0012 point 4 ("records from one service arrive in order") for every row the announcement might itself hold up. **This is scoped to `event.retried` specifically, not every `.change-recorded` event, and only on the "am I blocked" side** — two issues [Buddy]'s re-review of `0267446` correctly flagged: first, an earlier, broader version exempted any change record regardless of action (an ordinary `batch.loaded` record could have overtaken an earlier failed event of the same tenant and service); separately, a first attempt at narrowing it to `event.retried` still exempted the announcement from *blocking* too, which would have let a *stuck announcement* be jumped by a later, unrelated event — the same point-4 violation, just moved to a rarer trigger (Audit failing specifically on the announcement, not on an ordinary event). Only the retry's own announcement — a case decision 0019 did not anticipate, since it did not exist before this task — gets any exception at all, and only because without it a retry's audit trail could be withheld indefinitely by the very event it is retrying.
   - **What was discussed on the way here, now superseded:** [Claude]'s and [Buddy]'s first round of review (`PR #40`) each read the J file's "target the event ID, field `service`" differently — one put the service name in `targetType` (matching the original build), the other wanted it in neither `targetType` nor `targetId`, as a value that `ChangeRecordFields.fields` cannot actually carry (fields are names only, never values, by decision 0012's rule). A later round (`PR #38`) had already moved to a composite `targetId` (`<service>:<eventId>`) to match the `role.granted`/`role.revoked` pattern instead. All three read the same ambiguous line differently; rather than pick one, this was escalated and confirmed directly, landing on the shape above — simpler than any of the three, because `source` already carries the service without needing `targetType`, `targetId`, or `fields` to do that job.
5. **Not wired into `app/`'s `/status` route.** `http.ts`'s `/status` is explicitly "for the operator network only" with no actor yet (no sign-in: stream C); `deliveryProblemSummary` needs an `Actor`. Wiring it in now would mean inventing one for an anonymous endpoint. The function is ready for B/C to call once there is a real operator session; `/status` keeps using the unguarded `deliveryProblems` count it already had.

## Not in this task (per the J file)
Skipping or discarding an event, retrying every tenant's stuck events at once, and alerts.

## Resolved: durability (raised by [Buddy]'s review of PR #40, 2026-11-21; confirmed by the product owner the same day)

[Buddy] found a real gap in an earlier round of point 4 above: a direct, synchronous call to `app.audit.commands.record(...)` after `retryStuckEvent` had already committed was not durable. If the process stopped, or Audit was briefly unreachable, between the reset committing and the `record` call succeeding, the retry had already happened — the event was no longer stuck, so it could never be retried through this path again — but no `event.retried` record would exist, and nothing could create one later. This was not fixable by changing *which* Audit command is called (`record` vs. a hypothetical `recordOperation`): either way the write would be a separate step in a different service's schema from the reset, which rule 7 already says cannot share one transaction. The only way to make the announcement durable was to write it in the **same transaction as the reset**, which means going through the **retried event's own owning service's outbox** (`services/<name>/src/outbox.ts`), not a direct call from `app/`.

Three options were on the table: (A) each service's own outbox resets and announces atomically, reaching Audit through the normal drain pipeline; (B) a durable staging mechanism invented inside `app/` for pending announcements, a worse fit since `app/` owns no schema by design; (C) accept the gap as a documented limitation. **Option A is what point 4 above now describes and the codebase implements.** Its cost — touching every service's `outbox.ts`/`index.ts` (8 services) and adding a `change-recorded` event type to Exposure Analysis, the one service that did not yet have one — was confirmed as acceptable and necessary, larger than this task's original scoped files (Identity + `app/src/operations.ts`) but not a different task: the durability guarantee the J file implies for "every retry is recorded" cannot be built any other way. Closing the gap for real needed this; there is no cheaper correct version of it.

## Fixed from review: platform-role audit volume ([Claude]'s review of PR #40, 2026-11-21)

6. **A platform actor's single call now records `platform-role.used` once, not once per tenant it can see.** `visibleTenants` (used by `listDeliveryProblems` with no filter, and by `deliveryProblemSummary` always) checked every candidate tenant in a loop; `checkAccess` records a platform-role grant on every call (decision 0001), so one unfiltered call wrote one record into *every* active tenant's trail — three tenants meant three records for one logical "use", and polling `deliveryProblemSummary` for a badge would have kept doing this forever. Fixed: a platform actor's grant does not depend on which tenant is named (`decide()` short-circuits on the platform role before loading any tenant-specific fact), so one `checkAccess` call against any single candidate settles it for every candidate — allowed there means allowed everywhere; denied there means denied everywhere. A tenant-scoped actor still needs one check per candidate, since that is the only way to discover which (if any) tenant they administer. Verified by removing the short-circuit and watching the call-count regression fail (9 calls for 3 list/summary calls across 3+ tenants, instead of 3), then restoring it.

## Tests
`services/identity/src/access.test.ts`: only `TREASURY_ADMIN` and the platform role hold the permission. `app/src/operations.db.test.ts`: a viewer/analyst/reviewer/approver are refused for listing, summary and retry; a tenant admin sees and retries only their own tenant, and cannot retry another tenant's event even with its real ID; a non-stuck event is refused naming its state; a retried event is actually delivered on the next `drain`; the platform role sees and retries every tenant, may narrow by tenant, and its use is recorded (after a `drain`); an audit record (`event.retried`) exists for each retry, source naming the owning service and target the plain event ID, and the chain still verifies (a `drain` is needed first, since the announcement now arrives through the normal pipeline, not a synchronous write); a platform actor's three list/summary calls across three or more tenants make exactly three `checkAccess` calls, not one per tenant.

`app/src/end-to-end.db.test.ts` carries the atomicity, tenant-scope and ordering-exception regressions, since they exercise the retried event's whole real delivery path (dispatcher, outbox ordering, Audit), not just `operations.ts`'s guard logic:
- A failed announcement insert (a `KyselyPlugin` that throws on any insert into `outbox`, the same technique used for J1/J2's atomicity tests) leaves the reset rolled back too — the event is still stuck, `attempts` unchanged, no announcement recorded.
- `retryStuck` called directly against the outbox, with the right event ID but the wrong tenant, changes nothing and writes no announcement — proving the mutation enforces the tenant itself, not only `operations.ts`'s lookup above it.
- A retry's own announcement reaches Audit even while the event it is about keeps failing and reaches "stuck" a second time, without ever itself being delivered, proving the narrow exception actually does something (reverting it to exempt all `.change-recorded` events, not just `event.retried`, makes a *different* test fail: see next).
- An ordinary change record (not a retry) announced after an earlier failed event of the same tenant and service stays held behind it, exactly like any other event — proving the exception is narrow, not a blanket one (this is the test [Buddy]'s re-review asked for alongside the one above; reverting the narrowing to "any `.change-recorded`" makes this one fail, while the one above still passes).
- A retry announcement that itself fails to deliver (Audit made to throw for it specifically) still blocks a later ordinary event of the same tenant and service, exactly like any other row — proving the exception has no effect on the announcement's ability to block others, only on whether it can be blocked. Reverting to a version that also exempted the announcement from blocking makes this one fail while every test above still passes, so it is a distinct guarantee, not redundant with the two above it.
- A second, later stuck episode of the same event produces its own, separate record, distinct from the first.
- An actual duplicate delivery (not an empty repeat `drain`, which could pass without invoking Audit a second time): the exact persisted payload of an already-recorded announcement is redelivered directly to `audit.commands.record`, simulating a `drain` whose own `markPublished` step failed after Audit had already committed — Audit's existing dedup (decision 0012 point 5) returns `DUPLICATE` and the trail is unchanged.

The existing retry-and-redeliver test in the same file now expects 3 delivered events on the first `drain` after a retry (the retried event, the one that waited behind it, and the retry's own announcement), not 2.

Each new rule was broken and watched to fail, then restored: the platform-role volume fix, the atomicity of the reset-and-announce, the tenant scope on the mutation itself, and the ordering exception (both its existence and its narrowness).
