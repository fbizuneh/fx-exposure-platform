# 0030 — Stuck events: who may see and retry them

Date: 2026-11-21. Services: identity (permission), app/ (`operations.ts`). Source: `docs/release-1/J-backend-gaps.md` (J3), confirmed as decision row #8 (Overview table) by Fikre on 2026-11-20.

## Decided

1. **New permission `operations:manage-events`**, added to Identity's `PERMISSIONS`. Held by `TREASURY_ADMIN` (which is `new Set(PERMISSIONS)` — every permission, automatically) and by the platform role (`decide()` already allows `SYSTEM_ADMIN` everywhere, before any tenant-specific facts are even loaded). No other role's permission set lists it, so no other code change was needed in `roles.ts`.
2. **Guarded functions live in `app/src/operations.ts`, not in `dispatch.ts`.** `dispatch.ts`'s `deliveryProblems`/`retryStuckEvent` stay exactly as they are (decision 0019): unguarded primitives the drain loop and tests already use. `operations.ts` wraps them with `checkAccess` and returns the done-when shapes J3 asks for:
   - `listDeliveryProblems(app, actor, filter?)`: with `filter.tenantId` given, one `checkAccess` call against that tenant (works for both a tenant admin and the platform role — the platform role is allowed regardless of which real tenant is named, since `decide()` short-circuits before touching tenant facts). With no filter, the function discovers which tenants the actor may see by checking every tenant that is either active or currently has a delivery problem, and returns the union's events; if that set is empty, it refuses rather than silently returning nothing, so a role with no access anywhere is told so.
   - `deliveryProblemSummary(app, actor)` takes no tenant at all, so it always uses the same discovery path: counts are only ever taken over tenants the actor may see.
   - `retryDeliveryProblem(app, actor, { service, tenantId, eventId })`: one `checkAccess` against the named tenant, then looks the event up **within that tenant** from the raw `deliveryProblems` list before calling `retryStuckEvent` — `retryStuckEvent` itself has no tenant check, so this lookup is what stops a tenant admin reaching another tenant's event with a guessed ID. "Not stuck" is reported from the same lookup (the event is retrying automatically; there is no third state left once `deliveryProblems` already filters to `attempts > 0`).
   - Errors: a bad permission throws `AccessDenied` (same `not allowed (operations:manage-events): <reason>` shape Audit's own `access.ts` uses for `audit:read`); a missing or non-stuck event throws `RangeError` with the state named.
3. **Every use of the platform role is already recorded, for free.** `checkAccess` itself announces `platform-role.used` whenever `decision.via === "platform-role"` (decision 0001), so calling it from `operations.ts` for every list/summary/retry means the platform role's use of this permission lands in Audit with no extra code. That announcement goes through Identity's own outbox and needs a `drain` to reach the trail, like any other change record.
4. **The retry itself is recorded directly, not through a service's outbox.** `app/` already calls `app.audit.commands.record(...)` directly for the same reason `dispatch.ts` does — the composed `audit` object is not restricted to its published contract the way another *service* would be, since app/ is the composition root (rule 2 is about one service reaching another, not app/ reaching what it composed). There is no governing service whose transaction this write could join anyway: `retryStuckEvent` changes one service's outbox row, Audit's `record` changes Audit's own schema, and rule 7 forbids one transaction spanning both. So the two are necessarily two separate steps, exactly as the boundary rules already require for any two-service change — **no `recordOperation` addition to Audit's contract was needed.** The record: `type: "operations.change-recorded"` (so `source` reads "operations" in the trail — this action belongs to no domain service), action `event.retried`, `targetType` the service name (`"fx-rate"`, `"data-source"`, …) and `targetId` the event ID, `programId: null`, `fields: []`.
   - J3's text reads "target the event ID, field service"; I read "service" as needing to be *recoverable*, not literally listed as a changed field name with no value (decision 0012's own rule: an identifying detail goes in the target, not a field — the existing example is a role grant's target `<user>/<ROLE>`). Putting the service in `targetType` does that without inventing a "no values, except here" exception. Flagging this reading for Fikre to override if a different shape was intended.
5. **Not wired into `app/`'s `/status` route.** `http.ts`'s `/status` is explicitly "for the operator network only" with no actor yet (no sign-in: stream C); `deliveryProblemSummary` needs an `Actor`. Wiring it in now would mean inventing one for an anonymous endpoint. The function is ready for B/C to call once there is a real operator session; `/status` keeps using the unguarded `deliveryProblems` count it already had.

## Not in this task (per the J file)
Skipping or discarding an event, retrying every tenant's stuck events at once, and alerts.

## DECISION REQUIRED (raised by [Buddy]'s review of PR #40, 2026-11-21)

[Buddy] found a real gap in point 4 above: a direct, synchronous call to `app.audit.commands.record(...)` after `retryStuckEvent` has already committed is not durable. If the process stops, or Audit is briefly unreachable, between the reset committing and the `record` call succeeding, the retry has already happened — the event is no longer stuck, so it can never be retried through this path again — but no `event.retried` record exists, and nothing can create one later. This is not fixed by changing *which* Audit command is called (`record` vs. a hypothetical `recordOperation`): either way the write is a separate step in a different service's schema from the reset, which rule 7 already says cannot share one transaction. The only way to make the announcement durable is to write it in the **same transaction as the reset**, which means it has to go through the **retried event's own owning service's outbox** (`services/<name>/src/outbox.ts`), not a direct call from `app/`.

**Option A (recommended).** Each service's `outbox.ts` `retryStuck` takes the retry's audit fields (actor, and the service's own name for `targetType`) and, in one transaction, both resets the event and inserts a `<service>.change-recorded` announcement (`event.retried`) into *that service's own* outbox. It then reaches Audit through the existing drain → dispatch pipeline — durable, and automatically retried if Audit is briefly down, like every other change record. `operations.ts`'s `retryDeliveryProblem` passes the actor through `dispatch.ts`'s `retryStuckEvent` into this.
- Cost: touches every service's `outbox.ts` (currently near-identical per service, decision-0024-style) and `index.ts` (8 services), plus adding a `<service>.change-recorded` event type to the one service that does not yet have one (Exposure Analysis — decision 0032/J2 found it has no person-triggered command of its own, but this would still need the event *type* to exist for this operator-initiated case). A `source` of, say, `"fx-rate"` rather than `"operations"` for an `event.retried` record is arguably more accurate (it is that service's outbox that changed) but is a different framing than this PR currently uses.

**Option B.** Give `app/` its own durable staging mechanism for pending audit announcements, retried until Audit confirms them. Cost: `app/` owns no schema and no migrations by design (AGENTS.md's structure section); this would need one invented solely for this, which is a worse fit than writing to a service's own outbox that already exists for exactly this purpose.

**Option C.** Accept the gap as a documented limitation for this task; the audit record for a retry can be lost to a crash or an Audit outage between the two steps, with no reconciliation. Cheapest, weakest on correctness for data that exists specifically to be trustworthy.

**Not decided in this PR.** Option A is recommended but touches every service, which is larger than this task's scoped files (Identity + `app/src/operations.ts`); it should not be done without the product owner's confirmation. Until decided, the gap in point 4 stands as a known limitation, not silently fixed and not silently ignored.

## Tests
`services/identity/src/access.test.ts`: only `TREASURY_ADMIN` and the platform role hold the permission. `app/src/operations.db.test.ts` (new): a viewer/analyst/reviewer/approver are refused for listing, summary and retry; a tenant admin sees and retries only their own tenant, and cannot retry another tenant's event even with its real ID; a non-stuck event is refused naming its state; a retried event is actually delivered on the next `drain`; the platform role sees and retries every tenant, may narrow by tenant, and its use is recorded (after a `drain`); an audit record (`event.retried`) exists for each retry, and the chain still verifies. Each new rule (the access check, the tenant-scoped lookup, the stuck-state refusal, the audit record) was broken and watched to fail, then restored.
